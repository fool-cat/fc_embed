# `fc_stdio` 设计与实现说明

本文档对应以下代码:

- [fc_stdio.h](./fc_stdio.h)
- [fc_stdio.c](./fc_stdio.c)

## 1. 模块定位

`fc_stdio` 是 `core/` 里一套“极简版标准输出格式化框架”。

它的目标不是完整替代标准库 `stdio`，而是提供:

- `sprintf / snprintf`
- `fprintf / vfprintf`
- 一个统一的轻量输出抽象 `FC_FILE`

让上层可以把格式化结果输出到:

- 普通内存缓冲区
- `fc_fifo`
- `fc_port`
- `fc_log`
- 其他自定义后端

## 2. 总体分层

```text
+--------------------------------------------------------------+
|                        业务 / 上层模块                        |
|  fc_printf / fc_log_fprintf / fc_fifo_vprintf / 自定义输出    |
+-------------------------------+------------------------------+
                                |
                                v
+--------------------------------------------------------------+
|                          fc_stdio                            |
|  fc_sprintf / fc_snprintf / fc_vfprintf                      |
|  FC_FILE 抽象                                                 |
+-------------------------------+------------------------------+
                                |
                                v
+--------------------------------------------------------------+
|                    具体输出后端 / 适配层                      |
|  内存缓冲 / fifo / port / log / 自定义 write 回调            |
+--------------------------------------------------------------+
```

所以 `fc_stdio` 的本质不是“终端模块”，而是“格式化核心 + 输出抽象”。

## 3. `FC_FILE` 模型

整个模块最关键的是 `FC_FILE`:

```c
struct _FC_FILE
{
    char  *p_start;
    char  *p_now;
    char  *p_end;
    size_t n;

    void *user;

    union
    {
        fc_file_write_t write;
        fc_file_read_t  read;
    } io;
};
```

可以把它理解成:

- 一段当前可直接读写的内存窗口
- 外加一个窗口耗尽后的回调

### 3.1 内存窗口字段

- `p_start`
  当前窗口起点
- `p_now`
  当前读写位置
- `p_end`
  当前窗口终点
- `n`
  本次累计输出字节数

### 3.2 用户上下文

- `user`
  交给后端自己解释

例如:

- `fc_fifo_vprintf` 里把它当作 `fc_fifo_t *`
- `fc_log` 里把它当作 `fc_log_file_user_t *`

### 3.3 IO 回调

- `io.write`
- `io.read`

当前真正成熟使用的是写路径。

## 4. `FC_IO_SWAP` 和 `FC_IO_EOF`

`fc_stdio` 定义了两个很重要的控制值:

- `FC_IO_SWAP = 0`
- `FC_IO_EOF = -1`

它们不是普通数据长度，而是写回调的控制信号。

### 4.1 `FC_IO_SWAP`

表示:

- 当前内存窗口用完了
- 需要后端重新提供一段新的连续内存

典型用途:

- `fc_fifo_vprintf` 在一段线性可写区写满后，推进 FIFO，再申请下一段线性区
- `fc_log` 在一块日志内存块写满后，再申请下一块 pool block

### 4.2 `FC_IO_EOF`

表示:

- 本次格式化输出结束

后端可以在这个时机做最终提交，比如:

- 推进 FIFO 写指针
- 把日志块链入队列
- 做收尾统计

## 5. 输出路径的核心思路

`fc_vfprintf()` 的写字符过程可以概括成:

```text
优先往 p_now ~ p_end 这段内存直接写
        |
        v
如果窗口写满:
    调用 io.write(..., FC_IO_SWAP)
    由后端决定是否切到下一段窗口
        |
        v
全部格式化结束后:
    调用 io.write(..., FC_IO_EOF)
```

这套模型的优点是:

- 对简单内存输出非常直接
- 对 FIFO / log 这种“分段缓存输出”也很好扩展
- 上层格式化核心不用关心后端到底是数组、环形缓冲还是内存池链

## 6. API 分组

### 6.1 内存字符串输出

- `fc_sprintf()`
- `fc_snprintf()`
- `fc_vsprintf()`
- `fc_vsnprintf()`

适合:

- 直接格式化到 char 缓冲区

### 6.2 通用输出对象

- `fc_fprintf()`
- `fc_vfprintf()`

这是更底层的接口。

只要你能准备好一个 `FC_FILE`，就可以把格式化结果导到任何后端。

### 6.3 FIFO / port 对接

严格来说:

- `fc_fifo_vprintf()`
- `fc_port_vprintf()`

不在 `fc_stdio.h` 里声明为核心 API，
但它们都是基于 `FC_FILE + fc_vfprintf()` 这套机制实现的。

## 7. `fc_stdio.c` 的角色

`fc_stdio.c` 本身不是一个复杂实现文件，而是一个“统一编译入口”。

它直接 `#include` 了这些实现:

- `fc_sprintf.c`
- `fc_snprintf.c`
- `fc_vsprintf.c`
- `fc_vsnprintf.c`
- `fc_fprintf.c`
- `fc_vfprintf.c`
- `fc_fifo_vprintf.c`

这意味着:

- `fc_stdio.c` 更像一个聚合编译单元
- 真正的格式化逻辑主要在 `core/utils/` 下

这样做的好处是:

- 嵌入式工程里集成更直接
- 不需要在工程文件里单独管理太多小 `.c` 文件

## 8. 格式化能力来源

`fc_vfprintf.c` 明确说明它修改自 `xprintf`。

所以整体风格是:

- 轻量
- 面向嵌入式
- 功能集中在输出格式化

源码里还保留了几个能力开关:

- `XF_USE_LLI`
  是否支持 `long long`
- `XF_USE_FP`
  是否支持浮点 `%f/%e`
- `XF_DPC`
  小数点字符

因此 `fc_stdio` 不是“永远固定能力”的，它保留了根据平台裁剪格式化能力的空间。

## 9. `fc_fifo_vprintf()` 是怎么接进去的

`fc_fifo_vprintf()` 是理解整套抽象最好的例子。

它的工作方式是:

1. 先对 `fc_fifo_t` 调 `linear_write_setup()`
2. 把这段连续可写区挂到 `FC_FILE`
3. 调 `fc_vfprintf()`
4. 如果当前线性窗口写满，则通过 `FC_IO_SWAP` 推进 FIFO 并申请下一段窗口
5. 最后通过 `FC_IO_EOF` 提交最终写入长度

所以它不是简单地“每输出 1 个字符就调一次 FIFO 写接口”，而是优先利用连续窗口减少额外开销。

这也是 [fc_port.h](./fc_port.h) 和 [fc_log.h](./fc_log.h) 能够在格式化输出上复用 `fc_stdio` 的关键。

## 10. 当前边界

当前 `fc_stdio` 的设计边界很明确:

- 强调输出
- 不强调输入解析

头文件里也直接写了:

- “格式化解析 API 废弃实现，建议直接使用标准库”

也就是说，目前不要把它理解成一套完整的:

- `printf + scanf + FILE`

替代品。

更准确的理解应该是:

- 一套轻量、可嵌入式移植的 `printf` 核心

## 11. 在整个框架中的位置

`fc_stdio` 在 `core/` 的位置大致如下:

```text
+--------------------------------------------------------------+
|                   fc_log / fc_port / 业务输出                 |
+-------------------------------+------------------------------+
                                |
                                v
+--------------------------------------------------------------+
|                          fc_stdio                            |
|  FC_FILE / vfprintf / snprintf                               |
+-------------------------------+------------------------------+
                                |
                                v
+--------------------------------------------------------------+
|            内存缓冲 / fifo / pool block / 自定义写回调        |
+--------------------------------------------------------------+
```

它比 `fc_port` 更底层，也比 `fc_log` 更通用。

## 12. 使用建议

如果你要:

- 格式化到普通字符串

用:

- `fc_snprintf()`

如果你要:

- 格式化到 `fc_fifo`
- 再由 `fc_port` 或 DMA 异步发出去

用:

- `fc_fifo_vprintf()` / `fc_port_printf()`

如果你要:

- 把日志先格式化到分段缓存，再延迟输出

用:

- `fc_log_fprintf()`

也就是说，`fc_stdio` 最适合被当作“底层格式化引擎”使用，而不是直接当最终用户 API 暴露给所有业务模块。

## 13. 关键注意点

最后有几条实际使用时要注意:

1. `FC_FILE` 不是标准库 `FILE`
2. 当前主要实现的是输出，不建议依赖其输入解析能力
3. 写回调收到的 `len` 不只有正常长度，还可能是 `FC_IO_SWAP/FC_IO_EOF`
4. 是否线程安全由后端自己决定，`fc_stdio` 本身不加锁
5. `fc_stdio.c` 是聚合编译文件，工程集成时通常只需要把它加入编译即可
