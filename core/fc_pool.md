# `fc_pool` 设计与实现说明

本文档对应以下代码:

- [fc_pool.h](./fc_pool.h)
- [fc_pool.c](./fc_pool.c)

## 1. 模块定位

`fc_pool` 是 `core/` 里一套“固定块、可链式、支持连续块申请”的内存池管理器。

它解决的问题不是通用 `malloc/free` 的所有语义，而是嵌入式里更常见的这些需求:

- 固定内存池
- 单块分配尽量 O(1)
- 允许把多个块拼成一个逻辑对象
- 允许申请一段连续块
- 允许把若干逻辑对象压进 FIFO 再统一取走

所以它更适合做:

- 日志块缓存
- 固定块对象池
- 分段消息缓存
- 需要“固定块 + 链式拼接”的缓冲框架

而不是:

- 完整替代标准库堆分配器

## 2. 总体设计思路

`fc_pool` 的核心思路可以概括成三句话:

1. 把一大片内存切成很多个固定大小的节点
2. 空闲节点放在 `list_free`
3. 已分配节点既可以作为“连续块”，也可以作为“链式块”使用

整体关系如下:

```text
+--------------------------------------------------------------+
|                        上层模块 / 业务对象                    |
|  log block / 消息块 / 临时缓冲 / 自定义对象                   |
+-------------------------------+------------------------------+
                                |
                                v
+--------------------------------------------------------------+
|                          fc_pool                             |
|  list_free / fifo_used / alloc / free / malloc / realloc     |
|  连续块 / 链式块 / FIFO 化已用块                             |
+-------------------------------+------------------------------+
                                |
                                v
+--------------------------------------------------------------+
|                  用户提供的原始大块内存                       |
|      被切成 N 个 [header + payload] 固定节点                 |
+--------------------------------------------------------------+
```

## 3. 为什么它和普通内存池不太一样

很多固定块内存池只有两种状态:

- 块空闲
- 块已占用

而 `fc_pool` 还额外支持两种“组合能力”:

- 多个连续块表示一个更大的连续对象
- 多个不连续块可以通过 `next` 串成一条逻辑链

因此它不是单纯的 slab，也不是普通链表 allocator，更接近:

- 固定块池
- 连续块池
- 链式块池

三者的混合体。

## 4. 数据结构分层

### 4.1 `fc_pool_t`

`fc_pool_t` 是整个内存池对象，主要包含:

- `list_free`
  空闲链表头
- `fifo_used`
  已使用对象 FIFO 头
- `block_size`
  每块用户可用大小
- `record_min`
  历史最小剩余块数
- `mem_start / mem_end`
  静态池范围
- `sort_free_enable`
  是否启用排序释放

如果打开动态分配支持，还会多一个:

- `alloc_cb`

### 4.2 `fc_pool_header_t`

每一个固定块前面都有一个 header。

这个 header 不是单纯只存链表指针，而是复用了多个语义:

- 在空闲链表里:
  `linear_last` 表示当前连续空闲段的最后一个节点
- 在 FIFO 头里:
  `tail` 表示 FIFO 尾部
- 在普通节点里:
  `link_flag / block_count / used_size`

也就是说，`fc_pool` 的状态管理高度依赖 header 复用。

## 5. “连续块”和“链式块”是什么

这是理解 `fc_pool` 的关键。

### 5.1 连续块

连续块表示:

- 物理地址上相邻的多个固定节点
- 被当成一段更大的连续内存使用

在这种情况下，逻辑上它仍然只算“一个对象”，并且通常由:

- 第一块 header 记录 `block_count`
- 第一块 header 记录总 `used_size`
- `next == NULL`

来表示。

也就是说:

- 连续多块默认不会拆成链表逐块管理
- 它在外部看起来还是一个指针

### 5.2 链式块

链式块表示:

- 多个不连续节点
- 通过 `next` 连接成一个逻辑对象

这通常通过:

- `fc_pool_link(front, back)`

构造。

适合:

- 日志块追加
- 多段消息拼接
- 不要求整体物理连续、但需要逻辑连续遍历的场景

### 5.3 区别总结

```text
连续块:
    物理相邻
    一个头部描述多块
    更适合真正大块连续内存

链式块:
    物理可不相邻
    每段通过 next 串起来
    更适合逐块扩展
```

## 6. 初始化与切块

`fc_pool_init()` 会做这些事:

1. 清零 `fc_pool_t`
2. 记录原始内存区间
3. 对齐起始地址到 `sizeof(size_t)`
4. 计算每个节点真实大小:
   `header + payload`
5. 把整块内存切成一串固定节点
6. 建立 `list_free`
7. 让第一个空闲节点的 `linear_last` 指向当前整段连续空闲区的最后一个节点

因此初始化完成后:

- `list_free` 不只是一个空闲链表
- 它还天然保留了“当前有一整段连续空闲区”的信息

## 8. `fc_pool_alloc()` 与 `fc_pool_malloc()` 的区别

这两组接口语义并不一样。

### 8.1 `fc_pool_alloc()`

它只做一件事:

- 从空闲链表头剥离一个固定块

特点是:

- 静态池路径下尽量 O(1)
- 返回的是“一块”的用户地址
- `*size` 会被设置成当前块的实际可用大小

所以它更像:

- “拿一个固定块”

### 8.2 `fc_pool_malloc()`

它更接近标准 `malloc` 的使用方式:

- 若 `size <= block_size`，直接退化成 `fc_pool_alloc()`
- 若 `size > block_size`，尝试找一段足够长的连续空闲块

特点是:

- 最坏 O(n)
- 成功时返回一段连续用户内存
- header 会记录 `block_count`

所以它更像:

- “申请一段至少 size 字节的连续空间”

## 9. `sort_free_enable` 的取舍

这是 `fc_pool` 里最重要的策略开关之一。

### 9.1 关闭排序释放

也就是默认状态。

此时:

- 释放时直接把块挂回空闲链表头
- 单块释放更快
- `fc_pool_alloc()` 路径最轻

但代价是:

- 空闲链表不按地址排序
- 连续空闲块的组织会越来越碎
- 后续大块 `malloc` / 原地 `realloc` 成功率会下降

### 9.2 开启排序释放

调用:

- `fc_pool_sort_enable(pool, true)`

后，释放时会按地址插回空闲链表，并尽量恢复连续块信息。

优点是:

- 更利于后续连续块分配
- 更利于原地扩展 `realloc`
- `fc_pool_max_linear_*()` 更有意义

代价是:

- `free` 复杂度上升
- 插入和合并需要遍历

### 9.3 该怎么选

如果你的使用模式是:

- 主要单块分配 / 释放
- 很少申请大块连续空间

那保持默认更合适。

如果你的使用模式是:

- 经常 `fc_pool_malloc()` 大于单块的对象
- 希望 `realloc` 尽量原地扩展

那应该启用排序释放。

## 10. `fc_pool_free()` 做了什么

`fc_pool_free()` 比普通 fixed pool free 更复杂，因为它要处理:

- 连续块
- 链式块
- 动态块
- 排序 / 不排序两种回收策略

大致流程如下:

```text
拿到 ptr
    -> 回退到 header
    -> 区分静态块和动态块
    -> 如果是连续块,先拆回单节点
    -> 如果是链式块,按 next 遍历整条链
    -> 根据 sort_free_enable 选择:
         直接头插回 free list
         或按地址插回并恢复连续信息
    -> 动态块则走 alloc_cb(FREE)
```

所以 `fc_pool_free()` 的复杂度通常是:

- 至少和被释放对象包含的块数相关

这也是为什么头文件里明确写了:

- 单块 `alloc` 可做到 O(1)
- `free` / `realloc` 往往是 O(n)

## 11. `fc_pool_realloc()` 不是完整标准库语义

这是文档里必须单独强调的一点。

它支持这些情况:

- `ptr == NULL`
  等价 `fc_pool_malloc()`
- `size == 0`
  等价 `free`
- 目标仍在当前块数范围内
  仅修改 `used_size`
- 缩小
  释放多余连续块
- 扩大
  尝试在当前对象后面原地拿到更多连续块

但是它**不会像标准库 `realloc` 那样，在原地扩容失败时自动重新分配别处并拷贝旧数据**。

也就是说对静态池对象而言:

- 它更像“原地扩容尝试”
- 不是“完整搬迁式 realloc”

这是使用时非常重要的边界。

## 12. `fc_pool_mark_used()` 与 `used_size`

`fc_pool` 默认把新分配块先标成“全块已用”。

随后上层可以用:

- `fc_pool_mark_used(ptr, used_size)`

把它收缩成“实际用了多少字节”。

这在下面场景里非常关键:

- 日志块最终只写了部分字节
- `malloc` 得到的是多块连续空间，但实际内容没写满
- `fc_pool_fifo_walk()` 遍历输出时希望拿到真实有效长度

因此:

- `used_size` 不是装饰字段
- 它直接决定 walk / fifo_walk 给上层暴露的有效字节数

## 13. 链式遍历与 FIFO 化

### 13.1 `fc_pool_walk()`

遍历一个逻辑对象，不释放内存。

回调签名是:

- `walker(end, ptr, used, user)`

其中:

- `end`
  表示当前是否是这条逻辑链的最后一段
- `ptr`
  当前段用户地址
- `used`
  当前段有效数据长度

### 13.2 `fc_pool_fifo_push/pop/peek()`

这套接口把“一个逻辑对象”压进 `fifo_used`。

这里的 FIFO 元素不是单个节点，而是:

- 一整条链式对象
- 或一个连续块对象

所以 `fc_pool_fifo_pop()` 弹出来的也是一个对象头指针。

### 13.3 `fc_pool_fifo_walk()`

它会:

1. 从 `fifo_used` 里反复 `pop`
2. 对每个对象调用 `fc_pool_walk()`
3. 遍历完后自动 `fc_pool_free()`

所以它非常适合做:

- “生产者把对象塞进 FIFO”
- “消费者统一遍历并回收”

这也是 [fc_log.c](./fc_log.c) 默认后端能成立的基础。

## 14. `fc_pool_link()` 和 `fc_pool_merge()` 的区别

这两个 API 很容易混。

### 14.1 `fc_pool_link()`

语义是:

- 把两个逻辑对象链起来

要求不强调物理连续。

更适合:

- 非连续对象拼接

### 14.2 `fc_pool_merge()`

语义是:

- 尝试把两段物理连续的对象真正合并成一段连续对象

它要求:

- `front` 和 `back` 都必须是线性块
- 地址上必须相邻

如果成功:

- 会更新 `block_count`
- 会把数据整理成真正连续布局

所以它是“物理合并”，不是“逻辑链接”。

## 15. 动态内存支持

如果打开:

- `FC_FOOL_ENABLE_DYNAMIC_POOL_ALLOC`

那么 `fc_pool` 可以在静态池耗尽时额外走:

- `alloc_cb(MALLOC)`
- `alloc_cb(FREE)`
- `alloc_cb(REALLOC)`

默认还提供了弱实现:

- `fc_pool_dynamic_default()`

底层就是标准库:

- `malloc`
- `free`
- `realloc`

这意味着 `fc_pool` 可以工作在两种模式里:

1. 纯静态池
2. 静态池优先，失败后再走动态扩展

不过默认宏是关闭的，说明作者的主设计目标仍然是嵌入式固定内存模式。

## 16. 辅助宏

头文件里两个宏很实用:

- `FC_CALC_POOL_MEM_SIZE(block_size, block_count)`
- `FC_CALC_POOL_USABLE_SIZE(block_size, usable_size)`

它们的用途分别是:

- 已知块大小和块数，反推整池内存需求
- 已知想要的至少可用字节数，反推需要的整池内存需求

这比手算:

- header 开销
- 对齐开销

更稳妥。

## 17. 在框架中的位置

`fc_pool` 在 `core/` 里处于这种位置:

```text
+--------------------------------------------------------------+
|                      fc_log / 自定义消息池                    |
|  日志块 / 延迟输出块 / 固定块对象                             |
+-------------------------------+------------------------------+
                                |
                                v
+--------------------------------------------------------------+
|                           fc_pool                            |
|  固定块 / 连续块 / 链式块 / fifo_used                        |
+-------------------------------+------------------------------+
                                |
                                v
+--------------------------------------------------------------+
|                    用户提供的静态大块内存                     |
+--------------------------------------------------------------+
```

其中最典型的上层用法就是:

- `fc_log` 用它分配日志块
- `fc_log` 再把日志块链压入 `fc_log_pool` FIFO

## 18. 典型使用方式

### 18.1 固定块对象

```text
fc_pool_alloc()
    -> 拿一个固定块
    -> 使用
    -> fc_pool_free()
```

### 18.2 大块连续缓冲

```text
fc_pool_malloc(size > block_size)
    -> 找连续空闲段
    -> 成功后拿到一段更大的连续空间
```

### 18.3 链式日志块

```text
alloc block A
alloc block B
fc_pool_link(A, B)
fc_pool_mark_used(...)
fc_pool_fifo_push(pool, A)
消费者:
    fc_pool_fifo_walk(pool, walker, user)
```

## 19. 使用建议

适合:

- 固定块缓存
- 嵌入式日志池
- 分段消息缓存
- 静态内存优先的对象管理

不适合直接拿来做:

- 完全通用堆替代
- 强实时下的大量大块连续动态重排
- 需要标准 `realloc` 搬迁语义的场景

如果你要的是:

- 稳定固定块
- 明确内存上界
- 能链、能排队、能统计

那 `fc_pool` 很合适。

如果你要的是:

- 完全透明、和标准 `malloc` 一样的行为

那它不是那个目标。

## 20. 最重要的几个注意点

1. `fc_pool_alloc()` 是“拿一个固定块”，不是通用大块分配
2. `fc_pool_malloc()` 想申请多块连续空间时，更依赖 `sort_free_enable`
3. `fc_pool_realloc()` 主要是原地扩缩，不保证失败后自动搬迁
4. `fc_pool_link()` 是逻辑拼接，`fc_pool_merge()` 才是物理连续合并
5. `fc_pool_fifo_walk()` 会在遍历后自动释放对象
6. `used_size` 很重要，决定了 walk 时暴露给上层的真实数据长度
